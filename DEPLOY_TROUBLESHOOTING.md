# Устранение проблем с развертыванием

## Проблема: "connection timed out" при копировании файлов

Ошибка `dial tcp ***:***: connect: connection timed out` означает, что GitHub Actions не может установить TCP соединение с вашим сервером.

## Возможные причины и решения

### 1. Проверка SSH подключения

Сначала убедитесь, что вы можете подключиться к серверу с вашего локального компьютера:

```bash
ssh -p <PORT> <USER>@<HOST>
```

Если подключение не работает локально, проблема не в GitHub Actions.

### 2. Проверка порта SSH

**Проблема:** Неправильный порт в секретах GitHub.

**Решение:**
- Проверьте, что `DEPLOY_PORT` в GitHub Secrets соответствует реальному порту SSH на сервере
- По умолчанию SSH использует порт 22
- Если используется нестандартный порт (например, 2222), убедитесь, что он указан правильно

**Проверка на сервере:**
```bash
sudo netstat -tlnp | grep sshd
# или
sudo ss -tlnp | grep sshd
```

### 3. Файрвол блокирует соединение

**Проблема:** Файрвол на сервере или у провайдера блокирует входящие соединения.

**Решение:**

**На сервере (если используется UFW):**
```bash
sudo ufw allow <SSH_PORT>/tcp
sudo ufw status
```

**На сервере (если используется firewalld):**
```bash
sudo firewall-cmd --permanent --add-port=<SSH_PORT>/tcp
sudo firewall-cmd --reload
```

**Проверка iptables:**
```bash
sudo iptables -L -n | grep <SSH_PORT>
```

**Важно:** Убедитесь, что файрвол разрешает соединения с IP адресов GitHub Actions. GitHub Actions используют динамические IP, поэтому лучше разрешить все входящие соединения на SSH порт.

### 4. Сервер недоступен из интернета

**Проблема:** Сервер находится за NAT или имеет только приватный IP.

**Решение:**
- Убедитесь, что сервер имеет публичный IP адрес
- Проверьте настройки маршрутизации у провайдера
- Если используется VPN, убедитесь, что GitHub Actions может до него подключиться

**Проверка:**
```bash
# На сервере
curl ifconfig.me
# Должен показать публичный IP
```

### 5. SSH сервис не запущен или не слушает на правильном интерфейсе

**Проблема:** SSH сервис не запущен или слушает только на localhost.

**Решение:**

**Проверка статуса SSH:**
```bash
sudo systemctl status sshd
# или
sudo systemctl status ssh
```

**Запуск SSH (если не запущен):**
```bash
sudo systemctl start sshd
sudo systemctl enable sshd
```

**Проверка конфигурации SSH:**
```bash
sudo grep -E "^ListenAddress|^Port" /etc/ssh/sshd_config
```

Убедитесь, что SSH слушает на всех интерфейсах (0.0.0.0) или на публичном IP, а не только на 127.0.0.1.

### 6. Неправильный SSH ключ

**Проблема:** SSH ключ в GitHub Secrets не соответствует публичному ключу на сервере.

**Решение:**

**Проверка публичного ключа на сервере:**
```bash
cat ~/.ssh/authorized_keys
```

**Проверка приватного ключа локально:**
```bash
ssh-keygen -y -f <путь_к_приватному_ключу>
```

Публичный ключ, сгенерированный из приватного, должен совпадать с одним из ключей в `~/.ssh/authorized_keys` на сервере.

### 7. Альтернативное решение: Использование Git вместо SCP

Если SCP продолжает не работать, можно использовать Git для получения файлов на сервере:

**Обновленный workflow уже включает fallback**, но вы также можете полностью перейти на Git:

1. Клонируйте репозиторий на сервер:
```bash
cd /opt/java-course-site
git clone https://github.com/<owner>/<repo>.git .
# или если уже клонирован:
git pull origin main
```

2. Обновите workflow, чтобы использовать Git вместо SCP (уже частично реализовано в fallback).

### 8. Проверка логов SSH на сервере

Если подключение все еще не работает, проверьте логи SSH:

```bash
# На сервере
sudo tail -f /var/log/auth.log
# или
sudo journalctl -u sshd -f
```

Попробуйте подключиться снова и посмотрите, что появляется в логах.

### 9. Проверка GitHub Secrets

Убедитесь, что все секреты настроены правильно в GitHub:

1. Перейдите в Settings → Secrets and variables → Actions
2. Проверьте наличие всех необходимых секретов:
   - `DEPLOY_HOST` - IP адрес или домен (например, `5.129.200.192`)
   - `DEPLOY_USER` - пользователь для SSH (например, `root`)
   - `DEPLOY_PORT` - порт SSH (например, `22` или `2222`)
   - `DEPLOY_SSH_KEY` - приватный SSH ключ (весь ключ, включая `-----BEGIN ...` и `-----END ...`)
   - `DEPLOY_PATH` - путь на сервере (например, `/opt/java-course-site`)
   - `GHCR_TOKEN` - токен для GitHub Container Registry

**Важно:** При копировании SSH ключа убедитесь, что скопированы все строки, включая заголовки и переносы строк.

### 10. Тестирование подключения из GitHub Actions

Обновленный workflow теперь включает шаг "Test SSH connection", который поможет диагностировать проблему. Если этот шаг проходит, но SCP не работает, проблема может быть в самом SCP или в правах доступа.

## Быстрая диагностика

Выполните эти команды на сервере для быстрой диагностики:

```bash
# 1. Проверка SSH сервиса
sudo systemctl status sshd

# 2. Проверка порта
sudo netstat -tlnp | grep :22
# или для нестандартного порта:
sudo netstat -tlnp | grep :<PORT>

# 3. Проверка файрвола
sudo ufw status
# или
sudo firewall-cmd --list-all

# 4. Проверка публичного IP
curl ifconfig.me

# 5. Проверка SSH конфигурации
sudo sshd -T | grep -E "port|listenaddress"
```

## Рекомендации

1. **Используйте стандартный порт 22** для SSH, если это возможно
2. **Настройте fail2ban** для защиты от брутфорса
3. **Используйте SSH ключи** вместо паролей
4. **Ограничьте доступ по IP** только для GitHub Actions (если знаете их IP диапазоны)
5. **Мониторьте логи** для выявления проблем

## Если ничего не помогает

1. Попробуйте подключиться с другого сервера или через VPN
2. Проверьте настройки у провайдера хостинга
3. Рассмотрите использование GitHub Self-hosted Runner на вашем сервере
4. Используйте альтернативные методы развертывания (например, через webhook или CI/CD на сервере)
