# Оптимизация загрузки CPU

## Проблема
Сервер с 1 ядром CPU показывает 100% загрузку, хотя приложение не должно быть очень требовательным.

## Внесенные изменения

### 1. Ограничения ресурсов в Docker Compose
Добавлены ограничения CPU и памяти для всех контейнеров:
- **Backend**: максимум 0.7 CPU, 768MB памяти
- **Frontend**: максимум 0.4 CPU, 512MB памяти  
- **Nginx**: максимум 0.3 CPU, 128MB памяти
- **PostgreSQL**: максимум 0.5 CPU, 512MB памяти

Это предотвращает ситуацию, когда один контейнер "съедает" все ресурсы сервера.

### 2. Оптимизация JVM
В `backend/Dockerfile` добавлены параметры:
- `-Xmx512m` - максимум 512MB heap памяти
- `-Xms256m` - начальная heap память 256MB
- `-XX:+UseG1GC` - использование G1 garbage collector (оптимизирован для ограниченной памяти)
- `-XX:MaxGCPauseMillis=200` - максимальная пауза GC 200ms
- `-XX:+UseContainerSupport` - использование ограничений контейнера
- `-XX:MaxRAMPercentage=75.0` - использовать максимум 75% доступной памяти

### 3. Оптимизация пула соединений с БД
В `application-prod.properties`:
- Максимум 5 соединений (вместо 10 по умолчанию)
- Минимум 2 idle соединения
- Настроены таймауты для предотвращения утечек соединений

### 4. Оптимизация Nginx
В `nginx/nginx.conf`:
- `worker_processes 1` - один воркер для одноядерного сервера (вместо auto)
- `worker_connections 512` - уменьшено с 1024 для экономии памяти
- `use epoll` - более эффективный метод для Linux

## Потенциальные проблемы

### Компиляция Java кода
Сервис `JavaExecutionService` запускает процессы `javac` и `java` для выполнения пользовательского кода. Это **очень ресурсоемкая операция**, особенно:
- При одновременных запросах на компиляцию
- При компиляции больших файлов
- При длительном выполнении кода

**Рекомендации:**
1. Добавить rate limiting для эндпоинта компиляции
2. Ограничить количество одновременных компиляций
3. Рассмотреть использование очереди задач (например, RabbitMQ или Redis Queue)
4. Добавить кэширование результатов компиляции для одинакового кода

### Мониторинг
Используйте обновленный скрипт `diagnose.sh` для проверки:
- Использования ресурсов контейнерами
- Топ процессов по CPU в каждом контейнере
- Общей загрузки системы

## Применение изменений

**Важно:** Синтаксис `deploy.resources` работает в Docker Compose v2+. Если у вас старая версия, обновите docker compose или используйте альтернативный синтаксис с `mem_limit` и `cpus`.

1. Пересоберите образы:
```bash
docker compose -f docker-compose.prod.yml build
```

2. Перезапустите контейнеры:
```bash
docker compose -f docker-compose.prod.yml down
docker compose -f docker-compose.prod.yml up -d
```

3. Проверьте использование ресурсов:
```bash
./diagnose.sh
```

4. Проверьте, что ограничения применяются:
```bash
docker stats
```

Если ограничения не применяются (старая версия docker compose), можно использовать альтернативный синтаксис:
```yaml
backend:
  # ... другие настройки ...
  mem_limit: 768m
  cpus: 0.7
```

## Дополнительные рекомендации

1. **Мониторинг в реальном времени:**
   ```bash
   docker stats
   ```

2. **Проверка логов на ошибки:**
   ```bash
   docker compose -f docker-compose.prod.yml logs --tail=100 -f
   ```

3. **Если проблема сохраняется:**
   - Проверьте, нет ли других процессов на сервере, потребляющих CPU
   - Рассмотрите возможность масштабирования (больше CPU/памяти)
   - Добавьте rate limiting для API эндпоинтов
   - Используйте CDN для статических файлов
